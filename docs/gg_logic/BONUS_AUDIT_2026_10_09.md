## Вывод

**В проверенном текущем flow регистрационные 100 существуют как клиентская
прибавка, без записи начисления в БД.** Для зарегистрированного пользователя
расчёт не проверяет прохождение гостя. После обычного входа в существующий
аккаунт тоже может отображаться 100 при нулевых играх и инвайтах.

Повторный расчёт возвращает те же 100, а не накапливает ещё 100 при каждом входе.
Бонус прибавляется после отбора периода: он отображается даже в периодах, в
которых этот пользователь не регистрировался. Это отличается от новой модели
«одно начисление по дате регистрации».

## Старый flow по шагам

1. `FFAppState.hasGuestGetLichtwatt` — Boolean с default false, хранится в
   SharedPreferences `ff_hasGuestGetLichtwatt`. Он относится к устройству, не к
   Supabase user ID. В `app_state.dart` восстановление строки 36–37, setter 91–93.
2. `HomePage` без авторизации и с false ждёт 7 секунд, показывает `deinStart`,
   после закрытия ставит true. Это не проверка завершения игры или регистрации.
   Фрагмент актуального Dart: `home_page_widget.dart:103–129`.
3. `homePageGuestContent` переключается с `HomePageScoreEmpty` на
   `HomePageScore`. Гостевое значение последнего — литерал `100`. `deinStart`
   показывает `+ 100`, но не пишет очки в Supabase.
4. Обычный login/успешный OTP сбрасывает гостевой флаг в false. Начисления или
   переноса 100 в этих действиях нет. В `authDialog` проверены обычный login,
   OTP и вход после reset-password.
5. После входа `HomePageScore` вызывает `totalSumPeriodLichtwatt`, которая
   безусловно прибавляет 100. Гостевой флаг для этой суммы не нужен.
   `signInAfterOtpVerification` создаёт/обновляет имя и email профиля, очки не пишет.

Сейчас authenticated Home всегда строит `HomePageScore`. Старая развилка
«нет игр/инвайтов → пустой score» сохранена под `if (false)` и не выполняется.
Поэтому рассказ «до удаления было 0, после стало 100» объясняется механизмом
отображения, но причина исходного нуля по текущему коду не установлена. Нужно
сверить установленный build и воспроизвести с тем же аккаунтом; не выдавать
предположение про старую версию/загрузку/кэш за установленный факт.

## Что происходит в текущей Supabase

* `public.users.good_power` имеет default 0. Нет поля received_bonus, даты
  регистрационного бонуса или отдельной таблицы начислений 100.
* `auth.users.on_auth_user_signup → public.handle_user_signup` создаёт профиль
  при создании Auth user. Он не добавляет 100 новому пользователю.
* Использованный invite начисляет **10 пригласившему**, обновляет запись invite,
  его good_power/balance_energy/invites. Это другое начисление.
* `public.games.trigger_unified_game_processing → unified_game_processing`
  обновляет игровые суммы при успешном завершении игры; регистрационных 100 нет.
* Проверенные Auth Edge Functions создают/подтверждают аккаунт, но не пишут 100.

Из существующей суммы good_power нельзя определить, показывали ли человеку
гостевые 100. Не хранится ни сам guest-event, ни связь локального флага с аккаунтом,
ни история бонуса. Отдельные ручные изменения данных этим аудитом не проверялись.

## Как подготовлены варианты basic и RPC

Оба используют один файл `variants/shared/01_environment_bonus.sql`.
В БД будет `gg_v2.point_awards`: `user_id`, `test`, `reason='signup_bonus'`,
`amount=100`, `awarded_at`. Уникальный ключ `(user_id,test,reason)` гарантирует
одно начисление на пользователя **в каждой среде**, включая одновременные вызовы.
Это учёт начисления; флаг в users отдельно не требуется. `users.signup_test`
означает среду регистрации, а не факт получения 100.

Подготовленная политика: **каждому подтверждённому зарегистрированному аккаунту**,
не только прошедшему guest → новый signup. Гостевые очки остаются демо.

1. В новом signup сохранить среду регистрации; после подтверждения и готового
   профиля вызвать `ggClaimSignupBonus(Environment.test)` с активной сессией.
2. Сервер проверяет auth.uid, существование профиля и подтверждение email;
   вставляет 100, если такой записи ещё нет. При повторном login возвращает
   `created=false, awarded=true`, не начисляя второй раз.
3. Дата начисления в подготовленном SQL — `auth.users.created_at` в UTC,
   а не время первого login/внедрения миграции. Бонус входит только в свой период
   и All-Time, не в каждый месяц/сезон.
4. Basic получает бонусные данные через контекст и прибавляет их к клиентскому
   расчёту один раз. RPC делает эту сумму на сервере. На новых привязках убрать
   прежнюю безусловную +100.
5. Исторический backfill создаёт бонусы подтверждённым существующим аккаунтам
   до фиксации сезонов. Это выбранное правило миграции, не восстановление истории
   гостевого режима. Старые непомеченные аккаунты по default относятся к prod.

Ledger не увеличивает `users.good_power`: старые клиенты, которые продолжают
прибавлять 100 сами, от одной вставки ledger не начнут отображать +200.
Не добавлять ещё один UPDATE good_power +=100 без отдельной проверки потребителей.

Если заказчик потребует бонус только за guest → новую регистрацию, потребуется
другая политика и сохранение соответствующего события для новых пользователей.
Надёжно разделить прошлых пользователей по этому признаку уже нельзя.

## Обязательные уточнения интеграции после аудита live Auth

**Это подготовка; текущий FF flow ещё не изменён.**

* Сейчас handle_user_signup создаёт public.users до OTP. AFTER INSERT бонусный
  триггер из пакета увидит неподтверждённый email и не начислит 100. Поэтому
  вызов claim после успешного OTP обязателен, а не необязательный fallback.
* signInAfterOtpVerification при signup обычно найдёт готовый профиль и выполнит
  UPDATE. Среду signup_test надо передать и в эту ветку первоначальной регистрации,
  а не только в INSERT. Не менять среду регистрации при обычном login.
* Для подтверждённого сразу admin signup нужно передать доверенную среду до
  профильного INSERT/автовыдачи. Иначе default false может выдать prod-бонус
  тестовому аккаунту раньше, чем FF успеет обновить signup_test. Этот путь требует
  отдельной проверки перед внедрением, он не решён одной ручной FF-привязкой.
* Таблица допускает по одному бонусу в prod и test. Если один аккаунт используется
  в обеих средах, это две раздельные статистики; не описывать ключ как глобально
  одно начисление вне зависимости от среды.

harness с минимальными GamesRow/InvitesRow. Прошли 8 проверок: пустые игры/инвайты
дают 100 в Home/MVP/MAX/AVG, повтор не увеличивает сумму, другой пустой месяц

на устройстве и не перенос начисления в БД.
