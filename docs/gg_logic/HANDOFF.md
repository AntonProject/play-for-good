## Окончательные решения пользователя

Ранние сообщения содержат другие варианты правил. Для продолжения использовать
следующие более поздние решения:

* Категории: только Most Valuable Player (`valuable`) и Most Active Player
  (`active`). MVP = Good Power завершённых игр + использованных инвайтов
  пригласившего пользователя + регистрационный бонус. MAP = число завершённых игр.
* Стартовые **100 включать в MVP и общий итог один раз**. Для зарегистрированных
  хранить начисление в отдельной таблице бонусов, не маскировать его игрой/инвайтом.
  Учесть дату начисления в сезонных фильтрах; существующие клиентские +100
  не прибавлять второй раз при переходе на новый источник. Гостевые 100 остаются
  демонстрационными. Переделка гостевого режима не входит в текущую задачу.
* Total Good Power в шапке — общий All-Time всех пользователей. По всем
  обновлённым местам использовать согласованные формулы. All-Time включает
  сезоны и записи вне сезонных диапазонов, а не только сумму сезонных результатов.
* `2025/26`: **20.11.2025–31.08.2026 включительно**.
  `2026/27`: **01.09.2026–30.06.2027 включительно**.
  На следующий день после конца выполняется фиксация; это 1 июля для 2026/27.
  Это не правило «каждые 9 месяцев без паузы». Пользователь ранее подтвердил
  ежегодные будущие сезоны с сентября по июнь; admin-вариант позволяет менять
  будущие даты и отключать автопланирование. Исходное ТЗ задаёт только два сезона.
* Default периода: последний **начавшийся** сезон — текущий либо завершённый;
  во время межсезонья оставлять последний завершённый. Default категории MVP.
  Месяцы остаются, «Seit Beginn» заменить на «All-Time».
* После уточнения заказчика награды получают **топ-3 MVP и топ-3 MAP**.
  Их сохраняют в отдельной таблице по окончании сезона. MVP-награда остаётся
  при переключении на MAP, даже если текущая позиция в MAP ниже третьей.
  Награды закрытого сезона не пересчитываются после удаления старой игры.
  Ранее обсуждавшийся динамический прошлый топ этим решением заменён.
* Во время сезона текущие места показывать цифрами; новые медали/кубки — только
  из сохранённых итогов. Дизайн текущих обозначений пока не предоставлен.
* Правило отображения бейджей подтверждено 12 октября: **MVP всегда перед MAP**.
  В списке при All-Time и обоих месячных фильтрах показывать все полученные
  награды закрытых сезонов; при сезонном фильтре — только награды этого сезона.
  В профиле всегда все полученные награды, независимо от периода Stats.
  Не ограничивать последним завершённым сезоном и не сворачивать повторяющиеся
  награды разных сезонов в один Boolean-флаг. Внутри каждой категории локально
  установлен порядок от нового сезона к старому; отдельного указания клиента
  по внутреннему порядку не было. Изменения подготовлены локально в SQL/адаптере.
* Все существующие игры считать prod, добавить `test=false` по умолчанию.
  Новые игры/инвайты получают среду из FF Environment.test. Новый signup получает
  signup_test. Старые INSERT без флага остаются совместимыми.
* Нужны перенос соцсетей вверх профиля, периоды Stats, чёрный фон/белая галочка
  подтверждения при изменённом фильтре; убрать верхний overscroll без изменения
  нижнего поведения.
* Уточнение 13 октября: в профиле Punkte per Game сохраняет нынешнюю сумму
  €nergy, не среднее. Новая привязка stats.good_energy.value/rank. У Meine Games
  €nergy per Game остаётся средним. Supporters value=1 — старая заглушка;
  прежний social-ранг рассчитывает игры с sponsor_money > 0 и переносится на
  stats.sponsored_games.rank, не на stats.games.rank.

Новые SQL используют приватную схему **`gg_v2`**, публичные функции
**`gg_v2_*`**, Broadcast `gg:v2:stats`. Не смешивать со старой схемой/функциями
`gg_internal`/`gg_*` или каналом `gg:stats`.

RPC actions возвращают **один JSON**, не List<JSON> целиком:

* `ggV2Rankings` → players, top_players, current_user, total_good_power,
  total_good_power_all_time, period, available_periods, pagination.
  Текущего пользователя не искать по ID в загруженной странице:
  использовать current_user. Номера мест брать из rank, а не индекса страницы.
* `ggV2ProfileStats` → All-Time шапка, Stats выбранного периода, награды.
* `ggV2Games` → ограниченная история; `ggGamesRows` преобразует её в GamesRow.
* `ggLoadContext`/`ggLocalFromRows` — базовый вариант. Для widget Backend Queries
  использовать pure adapter при rebuild, а не одноразовый action до загрузки строк.

CLI регистрирует 7 определений basic, 7 rpc, 9 admin. Он **не настраивает**
Backend Queries, native widget bindings, изображения, форму админки или Supabase.
Панели-примеры в пакетах показывают использование данных; это не готовый импорт UI.

## Оставшиеся ограничения и точки внимания

* Аудит +100 от 9 октября: текущий FF добавляет 100 в расчётах независимо от
  прохождения гостя; в БД регистрационного начисления нет. Basic/RPC подготовлены
  для бонуса всем подтверждённым аккаунтам, не только guest → signup. Исторический
  backfill не восстанавливает неизвестную историю гостей. Подробнее в аудите выше.
* Live Auth создаёт профиль до OTP: claim после подтверждения обязателен.
  В signup-ветке signInAfterOtpVerification передавать signup_test и в UPDATE
  существующего профиля. Для подтверждённого сразу admin signup дополнительно
  решить передачу среды до профильного INSERT, иначе default false выдаст prod.
* Calendar SQL сейчас UTC, исторические поля сравниваются как UTC naive timestamps.
  Перед первой фиксацией сверить продуктовый timezone и исторические даты.
* Backfill +100 выполнить **до** первой фиксации завершённых сезонов, иначе бонус
  не попадёт в сохранённые итоги. Делать только после разрешения менять БД.
* Default false защищает старые данные/INSERT, но не фильтрует SELECT старых
  клиентов. Старые версии с прежними RLS могут увидеть новые test-игры.
  Решение для всех старых сборок не реализовано этим комплектом.
* RPC не скачивает все игры на телефон, но сам SQL всё ещё агрегирует историю.
  Это не постоянная таблица текущих агрегатов; проверить реальные индексы/EXPLAIN.
* Профильные организации/bio/соцсети/Posts не входят в stats RPC: сохранить
  соответствующие запросы. Для организаций сузить игры до открытого userId + test.
* Строка Supporters была заглушкой. sponsored_games — число игр с взносами,
  не число людей; не подменять смысл без согласования. Punkte per Game также
  сохранить суммой €nergy по уточнению 13 октября и NATIVE_BINDINGS.
* Оптимизация Home/Energy и всех остальных расчётов не включена автоматически
  в вариант RPC. Разделение test/prod у их запросов — общее дополнение.

## Как продолжать

1. Прочитать этот файл, START и README выбранного пакета. Проверить `git status`.
2. Пока команда только «подготовить», допустимы локальные изменения и проверки.
   Не применять SQL и не запускать CLI с --apply.
3. После команды на внедрение использовать выбранный 02_rpc. Сохранить текущий Commit
   FF, при наличии возможности создать рабочую FF-ветку, получить её project ID.
4. Перед облачной работой обновить FF snapshot, сверить схему/права/данные Supabase
   в режиме чтения; определить timezone, бонусный backfill и границы среды.
5. После прямой команды на изменение БД применить выбранный install, индексы,
   backfill, первичное закрытие; настроить Cron по START. Не запускать весь SQL
   пакет вслепую поверх другой редакции схемы.
6. После команды на перенос в FF выполнить CLI dry-run на целевой ветке,
   затем apply; проверить Custom Code/compile. Настроить страницы вручную по
   NATIVE_BINDINGS, обновить флаги среды по QUERY_MAP.
7. Пройти пользовательские сценарии в тестовой сборке: бонус, оба топ-3,
   границы периодов, фильтры, обновления после своей/чужой игры, среда, возврат,
   reconnect, ошибки RPC, награды закрытого сезона и скролл. Обновить статус здесь.
