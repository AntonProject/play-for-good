# Объём задачи и варианты оценки — 1 октября 2026

Работа пока только локально. Облачные FlutterFlow и Supabase не изменять
без команды владельца. Этот документ уточняет текущий комплект: существующие
RPC/фиксация ещё не обновлены под test/prod и новый учёт стартового бонуса.

## Три варианта основного объёма

| Вариант | Часы основного объёма | Что включено |
| --- | --- | --- |
| ТЗ с сохранением существующих запросов | 8–10 | Две страницы, картинки/иконки, фильтры по двум заданным сезонам, общий итог, профиль/соцсети, топ-3 MVP/MAP закрытого сезона; таблицы сезонов/результатов и серверное закрытие; без общего переноса текущих расчётов на RPC |
| ТЗ + оптимизация расчётов | 14–16 | Предыдущий вариант + серверные текущие рейтинги, итоги и статистика, пагинация Meine Games; привязки JSON и listener на Good Games/профиле |
| ТЗ + оптимизация + админка сезонов | 18–20 | Предыдущий вариант + создание/редактирование запланированных сезонов, динамические фильтры по данным таблицы, закрытие по датам, автоматическое планирование следующего сезона |

Это вложенные оценки, а не часы, которые нужно складывать. Админка —
независимое дополнение: базовое ТЗ + админка без оптимизации ориентировочно
12–14 часов основного объёма. Оценка +4 часа подразумевает простую форму,
проверку дат/пересечений и существующую авторизацию админа. Редактор итогов,
повторное открытие закрытого сезона и расширенная панель тестирования туда не входят.

Новые пожелания ниже не были частью исходного ТЗ. Общая дополнительная строка
для любого варианта: test/prod, перенос бонуса в БД, верхний overscroll и
регрессионная проверка — ориентировочно 3–5 часов. Если их включать в общую
цену, ориентиры становятся 11–15 / 17–21 / 21–25 часов. До согласования
пакета не обещать исходные 8–10 за всё расширенное задание.

Оптимизация здесь ограничена Good Games и профилем. Полное устранение расчётов
на фронте в Home/Energy/админке и дополнительных диалогах требует отдельного
прохода по потребителям. Базовый вариант сохраняет ограничения старых запросов
по доступным инвайтам, объёму выгружаемых строк и скорости.

## Совместимость test/prod

В существующем экспорте есть FFDevEnvironmentValues().test и organization.test.
У games/invites такого поля нет. Владелец подтвердил: все имеющиеся игры — prod.

Новая колонка games.test BOOLEAN NOT NULL DEFAULT FALSE:
старые игры получают false; старые INSERT без поля также получают false.
В новой сборке при создании игры записывать значение FF Environment test.
Отдельно фильтровать чтения/счётчики, серверные расчёты, историю и итоги сезона.
В результаты добавить среду и составной ключ: season_id + test + user_id;
закрытие тестового результата не закрывает production-результат.

Тестовые приглашения и начисления тоже нужны со своей средой, иначе тестовые
очки попадут в prod-рейтинг через другой источник. Админские списки могут
показывать оба окружения с явным фильтром и отметкой.

Важно: DEFAULT не фильтрует чтения старого приложения. Реальная SELECT policy
games сейчас разрешает чтение всех строк. Новая prod-сборка с фильтрами будет
чистой; старая сборка без фильтров может увидеть новые test-записи. Если требуется
защита всех старых сборок, нужен отдельный режим доступа RLS для тестировщиков
или отдельная тестовая БД. Одного флага FlutterFlow для этого недостаточно.

## +100 Good Power — уточнённое правило

Владелец подтвердил: бонус входит в MVP и общий итог один раз. Это отдельное
начисление, а не фиктивная игра/приглашение. Предлагаемая таблица point_awards:
id, user_id, test, reason=signup_bonus, amount=100, awarded_at.
Уникальность user_id + test + reason защищает от повторного начисления внутри
окружения. Фиксированную сумму/источник и создание записи контролирует сервер.

All-Time включает запись всегда; сезон/месяц — только если awarded_at входит
в границы. MAP по-прежнему считает завершённые игры, бонус его не увеличивает.
При фиксации сезона учитывать бонус в MVP; его место остаётся сохранённым.

Для существующих зарегистрированных профилей добавить запись один раз с
достоверной датой регистрации. Проверить users.created_at/auth.users, не ставить
всем сегодняшнюю дату. У гостя сейчас нет документа; показанные 100 остаются
демонстрационными, до регистрации не входят в реальный общий итог.

На новом клиенте убрать постоянные +100 из getUserRatingScore,
totalSumPeriodLichtwatt, totalSumMAX/AVG и новых привязок профиля;
использовать данные БД. Старые сборки эту отдельную таблицу не читают, поэтому
их существующее прибавление 100 само по себе не станет двойным начислением.
Не писать бонус в games/invites: их старые суммы уже увеличились бы на бонус.

## Сезоны и админка

Из ТЗ: 2025/26 = [2025-11-20, 2026-09-01),
2026/27 = [2026-09-01, 2027-07-01). 30 июня входит полностью; закрытие с 1 июля.
Сентябрь–июнь — 10 календарных месяцев. Непрерывный цикл по 9 месяцев из ТЗ
не следует; старт 1 июля и конец 31 марта были бы отдельным новым правилом.
Следующие периоды по подтверждению владельца — ежегодно сентябрь–июнь.

В базовом варианте два сезона заполняются заранее; сервер закрывает известный
сезон по его дате. Автосоздание следующих записей и управление датами не входят.

Для пакета с админкой единственный источник дат/названий — таблица seasons.
Форма: название, год плашки, дата начала/последнего дня, статус, дата фиксации.
Редактировать незакрытые/запланированные сезоны; запрещать пересечения и end<start.
Даты уже закрытого сезона не менять без отдельной процедуры пересчёта.

Cron 1 июля фиксирует завершённый сезон и создаёт следующий запланированный,
если такого ещё нет. Его старт остаётся 1 сентября, не 1 июля. Создание записи
не означает немедленное начало соревнования. Cron не перезаписывает существующий
следующий сезон, если админ уже изменил его даты. Изменять таблицу могут только админы.

Клиент загружает текущий (последний начавшийся) и предыдущий сезон из таблицы,
плюс фиксированные last_month/this_month/all_time. Для июля/августа default —
последний законченный сезон. Новый сезон становится default на дату начала.
Фильтры/название/год не требуют ежегодного обновления приложения.

## Проверка победителей

Итоги не редактировать вручную для основного теста: это не проверяет расчёт.
Создавать test=true игры и инвайты известных игроков с известными очками/датами;
для проверки границ использовать последний день сезона и начало следующего.
Проверить: MVP с инвайтами/бонусом, MAP только по играм, обе тройки независимо,
текущий лидер без новой медали, медали после закрытия, сохранность MVP при MAP=5,
повторный запуск, prod/test изоляцию и отсутствие бонуса дважды.

Предпросмотр закрытия должен читать данные без записи production-итогов.
Проверку будущего закрытия выполнять в отдельной локальной БД или на специальном
тестовом сезоне. Не менять системное время/даты продового сезона. Тестовые итоги
хранятся отдельно по среде; обычный повтор запуска не перезаписывает фиксацию.

## Верхний overscroll

Подготовлен GgScrollBoundary: Custom Widget с Widget Builder для существующего
scrollable. На iOS запрещает выход за верхнюю границу, сохраняя нижний bounce;
на Android сохраняет обычную physics. Не использовать Custom Action для сброса
scroll offset: physics должна участвовать в самом движении.

Если нужно только скрыть белый фон, можно вынести красный фон в неподвижный
Stack вне scrollable. Это другое визуальное поведение; ограничение physics
устраняет именно верхнее растягивание. Не отключать всю прокрутку страницы.
