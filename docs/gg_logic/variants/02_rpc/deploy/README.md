# SQL Editor: поэтапное внедрение

**Этот порядок заменён последней командой 13 октября.** Сейчас использовать
[iteration1](../iteration1/README.md): сначала RPC/среды/календарь, бонус последним.
Файлы ниже сохранены как предыдущий план; не запускать их по этой инструкции.

Файлы собраны локально 13 октября. В рабочей Supabase ничего не выполнялось.
Открыть Supabase → SQL Editor → New Query, вставить нужный файл целиком и Run
от имени владельца **после команды на соответствующий этап**.
Не выполнять все пять файлов сразу и не заменять их полным install.sql.

| Файл | Назначение / когда запускать |
|---|---|
| 01_passive.sql | Новая схема, поля и определения RPC. Без бизнес-триггеров, backfill, фиксации и Cron. Клиентское начисление закрыто; новые RPC чтения доступны |
| 02_backfill.sql | Записать +100 подтверждённым существующим аккаунтам в новую таблицу по Auth.created_at, один раз. До итоговой сверки MVP; исходные игры/инвайты/балансы не увеличиваются |
| 03_finalize_2025_26.sql | После проверки топа сохранить результаты завершённого 2025/26; текущий 2026/27 не закрывается |
| 04_activate.sql | После проверки signup/RLS/среды: разрешить claim бонуса и подключить дополнительные триггеры |
| 05_schedule.sql | После включения Supabase Cron: автоматическое закрытие заданных сезонов. Новый сезон автоматически не создаётся |

Скрипт 01 откажется работать, если gg_v2 бизнес-триггеры уже подключены:
он не отключает существующую автовыдачу при повторном запуске.
Изменения старых gg_* или существующих политик public этим пакетом не выполняются.
Новые поля games.test/invites.test/users.signup_test имеют NOT NULL DEFAULT false.
Старые данные относятся к prod; INSERT без поля остаётся prod. Перед live-запуском
сверить отсутствие одноимённых несовместимых полей/объектов и схемные права.

Индексы shared/05_indexes.sql отдельно, каждый CREATE INDEX CONCURRENTLY вне
транзакции. Проверить существующие индексы/EXPLAIN до добавления.
В фазах 01 и 04 добавлен NOTIFY pgrst для обновления кеша Data API.

После 01 можно проверять чтение, но регистрационных 100 и сохранённых медалей
ещё нет. После 02 — корректно сравнивать очки/топ с учётом бонуса; после 03 —
проверять медали. Не выдавать пустую новую таблицу бонусов за итоговый рейтинг.

Все создания/регистрации/claim и игровые записи — отдельная проверка, не часть
пассивного чтения исторических данных. Старые приложения не фильтруют test:
тестовые игры в общей БД могут попасть в их старые расчёты.

Пересборка пяти файлов без подключения к БД:

```sh
python3 docs/gg_logic/variants/02_rpc/build_deploy_phases.py
```

Проверочный сценарий: variants/tests/check_deploy_phases.py, только новая локальная
фикстурная БД. Проверяет отсутствие триггеров/claim в фазе 01, повторный backfill,
прошлый сезон и отказ пассивной переустановки после активации.
