## До начала облачной работы

1. Сохранить **Commit в FlutterFlow**, затем рабочую FF-ветку, если позволяет тариф.
   Локальные файлы не являются резервной копией визуального проекта FF.
2. Использовать выбранный 02_rpc; дополнения согласовать отдельно.
   Не применять старый и новый SQL вперемешку.
3. Проверить схемы `auth.users` и `public.users`, дату регистрации, подтверждение
   почты, временную зону. Здесь существующие наивные даты сравниваются с UTC-календарём.
   Если продукт считает календарь в другой зоне — поменять config и согласовать
   интерпретацию исторических дат до первой фиксации.
4. Согласовать порядок бонусного backfill **до** сохранения результатов прошлого
   сезона. Зафиксированные результаты не исправляются обычным повторным запуском.
5. Картинки и актуальный дизайн текущих мест добавляет владелец. Панели здесь
   демонстрируют привязки и содержат временные обозначения наград.

## SQL для выбранного комплекта

Для выбранного RPC первым этапом применять **deploy/01_passive.sql**, а не полный
install.sql. Пять подготовленных этапов описаны в [deploy/README](02_rpc/deploy/README.md).
Локальная сборка для чтения — [LOCAL_PREVIEW](02_rpc/LOCAL_PREVIEW.md).
Полный install.sql ниже оставлен как единый комплект для согласованного полного
внедрения; он сразу подключает дополнительные триггеры.

Готовые собранные файлы находятся в `01_basic/install.sql`, `02_rpc/install.sql`,
`03_seasons_admin/install.sql`. Их можно пересобрать локально:

```sh
python3 docs/gg_logic/variants/build_sql.py basic --output docs/gg_logic/variants/01_basic/install.sql
python3 docs/gg_logic/variants/build_sql.py rpc --output docs/gg_logic/variants/02_rpc/install.sql
python3 docs/gg_logic/variants/build_sql.py admin --output docs/gg_logic/variants/03_seasons_admin/install.sql
```

Скрипт только пишет файл. Применение — отдельно по команде владельца.
Новый private schema `gg_v2` и имена `gg_v2_*` не заменяют старые `gg_*`.
`gg_v2` **не включать в exposed schemas Data API**. Публичные RPC возвращают
только публичную статистику; закрытие/начисления закрыты от произвольных записей.

После применения выбранного install:

```sql
-- Владелец БД. Начислит только зарегистрированным профилям с подтверждённой
-- почтой в Auth, по auth.users.created_at, без записи в игры/инвайты.
select gg_v2.ensure_signup_bonus(u.id,u.signup_test) from public.users u;
-- Затем первоначальное закрытие завершённых сезонов.
select gg_v2.finalize_due_seasons();
```

Индексы `shared/05_indexes.sql` применяются отдельно вне транзакции после проверки
существующих. Cron `shared/06_schedule.sql` — после включения Supabase Cron.
Ежечасно он закрывает завершившиеся периоды: конец 30 июня включительно,
фиксация с 1 июля. Работа самого облачного Cron локально не проверена.

Для admin владелец отдельно вносит доверенные ID:

```sql
insert into gg_v2.season_admins(user_id) values ('ADMIN_UUID') on conflict do nothing;
-- Если следующие даты ещё не согласованы заказчиком:
update gg_v2.calendar_settings set auto_plan=false where singleton;
```

## Общие изменения в FF

* Обновить Supabase schema. При создании игры и приглашения писать
  `test = FF Environment.test`. В новом signup INSERT профиля писать
  `signup_test = FF Environment.test`; при первоначальном signup также в UPDATE,
  если профиль уже создан Auth-триггером. При обычном login поле не менять.
* После успешного OTP/создания профиля **обязательно** вызвать `ggClaimSignupBonus(test)`.
  Не начислять деньги/очки клиентской вставкой. Повторный вход безопасен.
  INSERT профиля старым приложением автоматически создаёт prod-бонус, если
  Auth-аккаунт уже подтверждён; для остальных начисление доберёт claim/backfill.
  Live handle_user_signup создаёт профиль до подтверждения, поэтому его INSERT
  сам по себе бонус не обеспечит. Для admin signup с сразу подтверждённой почтой
  отдельно передать среду до INSERT: default false иначе выдаст prod-бонус.
* На обновляемых виджетах использовать сумму из нового источника **без +100**.
  Гостевые 100 остаются демонстрационными и не входят в реальную статистику.
* Все чтения игр в новой prod-сборке фильтровать `test=false`, в тестовой — true:
  см. [карту потребителей](QUERY_MAP.md). Фильтровать также инвайты и счётчики.
* Для скролла общий Custom Widget `GgScrollBoundary` с Widget Builder `content`:
  обернуть существующий scrollable, width/height по его контейнеру.
  Не ставить в тот же scrollable явно заданную BouncingScrollPhysics, которая
  перекроет ScrollConfiguration. Это не Custom Action. Пример проверен на iOS physics.

### Совместимость старых сборок

Default false сохраняет старые игры/INSERT. **Он не фильтрует SELECT старого
клиента.** Новые test-записи могут быть видны старым сборкам с нынешними RLS.
Пакет обеспечивает разделение новых запросов/RPC/итогов. Защита всех старых
сборок потребует отдельной серверной политики для доверенных тестировщиков
или отдельной тестовой БД; текущие live policies этим комплектом не заменяются.

Старые сборки не читают отдельную таблицу бонусов, поэтому их прежнее +100
само по себе не удвоится. Другие старые расчёты в Home/Energy пока могут иметь
прежние ошибки периодов. Оптимизация этих экранов не входит в вариант 02.

## Проверка

SQL всех трёх вариантов проверен в одноразовой локальной БД: начисление один
раз, период бонуса, обе среды, MVP/MAP, границы и сохранение сезона, права,
предпросмотр, даты админки, следующий сезон и повторное применение SQL.
Отдельно проверяется совпадение базовых Dart-расчётов с RPC на тех же данных.
Проверки не подтверждают скорость реальной БД, FF cloud compile или полный
визуальный импорт. После ручных привязок нужен проход тестовой сборки.

Перед live-применением проверить объём и EXPLAIN. Текущий RPC агрегирует данные
в БД, не выгружает все игры на телефон, но не является постоянной таблицей
агрегатов: стоимость SQL растёт с историей.
