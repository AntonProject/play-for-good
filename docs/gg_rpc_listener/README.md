# Пример RPC + listener для FlutterFlow

Актуальный комплект для всего ТЗ: [Good Games local logic](../gg_logic/README.md).
Этот файл описывает ранний неполный пример и не является инструкцией для применения.

Это локальный пример подключения, не применённый к FlutterFlow или Supabase.
Расчётная часть демонстрирует статистику одного профиля: Good Power, количество
игр, Good Power за игру и места среди всех пользователей. Полный список игроков,
награды, Supporters и показатели Home/Energy в этот пример не входят.
Существующие функции, включая их отображаемые +100, не изменены.

## 1. Supabase

`example.sql` создаёт RPC `gg_profile_stats`, внутреннюю функцию расчёта и
уведомления об изменениях. Скрипт применять только после отдельной команды
владельца проекта. Сейчас он не выполнялся на базе и не проверен запросом к ней.

Контракт:

```sql
select public.gg_profile_stats('<UUID профиля>', 'season_2026_27');
```

Допустимые `period`: `auto`, `season_2025_26`, `season_2026_27`, `last_month`,
`this_month`, `all_time`. В интерфейсе можно показывать привычные названия,
а в RPC передавать эти ключи. Даты на фронте вычислять не нужно.

`auto` выбирает последний начавшийся из двух заданных сезонов, в том числе
закончившийся. Будущие сезоны нужно добавлять в список внутри функции.
Даты сезонов включают весь последний день через исключающую верхнюю границу.
Месяцы в примере считаются по UTC: перед применением подтвердить часовой пояс
проекта и смысл `game_date`/`used_at`, которые имеют тип timestamp без timezone.

Good Power = LW завершённых игр + LW использованных приглашений.
Среднее = LW завершённых игр / количество завершённых игр (приглашения исключены).
В рейтинг входят все строки `users`, включая пользователей без очков.
Одинаковые значения получают одинаковое место (`rank`), с пропуском следующих
номеров. Это правило примера, его необходимо согласовать для выдачи наград.
All-Time включает записи без даты; сезон/месяц учитывают только записи с датой
в выбранном диапазоне. Отображаемые стартовые +100 не включаются в расчёт RPC.

Внутренняя функция намеренно читает приглашения всех пользователей: обычная
RLS-политика `invites` разрешает чтение только пригласившему пользователю,
что недостаточно для глобального рейтинга. Наружу возвращаются только публичные
показатели; строки приглашений и почта не возвращаются. `gg_internal` должен
оставаться вне списка exposed schemas в Data API. RPC доступен также гостям.

После изменения значимых полей игр/инвайтов триггер отправляет публичный
Broadcast: topic `gg:stats`, event `changed`, payload с временем изменения.
В payload нет записей игры/инвайта или персональных данных. Это уведомление,
а не готовая статистика. Создание/удаление пользователя тоже посылает сигнал.
Для этого подхода не нужно включать Postgres Changes для `games`/`invites`.
Нужно проверить наличие `realtime.send(jsonb,text,text,boolean)` и разрешение
публичных Broadcast-каналов в данном проекте Supabase.

## 2. FlutterFlow: Custom Action

Создать `ggProfileStats`:

- `userId`: String, required.
- `period`: String, required.
- Return Value: JSON, не List of JSON.

Вставить код из `gg_profile_stats.dart` под автоматическими импортами FlutterFlow.
Это асинхронный Custom Action; обычная Custom Function RPC не вызывает.
Для чужого профиля передавать ID открытого профиля, а не ID авторизованного юзера.

## 3. FlutterFlow: Page State и Action Block

На странице профиля:

- `selectedPeriod`: String, например `auto` по умолчанию.
- `profileStats`: JSON, nullable.
- `statsError`: String, nullable, если нужно показывать ошибку загрузки.

Создать Page Action Block `reloadProfileStats`:

1. Call Custom Action `ggProfileStats(profileUserId, selectedPeriod)`.
2. Из результата проверить `$.user_id == profileUserId` и
   `$.requested_period == selectedPeriod`. Если параметры уже поменялись,
   старый ответ не записывать: listener выполнит следующий запрос.
3. Только если страница ещё открыта и параметры совпали, Update Page State:
   `profileStats = Action Output`. Стандартные generated действия FF обычно
   проверяют mounted; это нужно проверить при подключении callback в FF.
4. При ошибке оставить предыдущие данные, показать ошибку/предложить повторить.
   Не подставлять ноль вместо ошибки сети. Использовать error branch действия FF
   или обработать ошибку в своём Action Block.

Привязки существующих строк статистики:

| Строка/поле | JSON Path |
| --- | --- |
| Good Power value | `$.stats.good_power.value` |
| Good Power number/rank | `$.stats.good_power.rank` |
| Good Games value | `$.stats.games.value` |
| Good Games number/rank | `$.stats.games.rank` |
| Punkte per Game value | `$.stats.good_power_per_game.value` |
| Punkte per Game number/rank | `$.stats.good_power_per_game.rank` |
| Total Good Power выбранного периода | `$.total_good_power` |

Числа форматируются текущими функциями форматирования. Параметры
`UserProfileInfoStatsRow` менять не нужно: уже принимает title/value/number.
Показатель верхней шапки профиля и её +100 требуют отдельной привязки согласно
текущему правилу отображения; не заменять её автоматически сезонным значением.

## 4. FlutterFlow: Custom Widget

Создать `GgStatsListener`, код из `gg_stats_listener.dart`:

- стандартные `width`, `height`: Double;
- `refreshKey`: String, required;
- `onRefresh`: Action без аргументов, required.

Добавить один экземпляр на страницу профиля, размер 1 × 1. Он не рисует UI.
Оставить widget смонтированным: не помещать под Conditional Visibility,
удаляющую его из дерева, или в удаляемую вкладку/элемент списка.

`onRefresh` → выполнить Page Action Block `reloadProfileStats`.

`refreshKey` → Combine Text из ID открытого профиля, выбранного периода и
`AppState.refreshDate`, с разделителями. Например:

```text
<profileUserId>|<selectedPeriod>|<refreshDate>
```

Listener вызывает callback:

- при первом показе страницы;
- при изменении `refreshKey` (фильтр/профиль/ручное обновление);
- после Broadcast-сигнала, в том числе об играх других пользователей;
- после подключения/переподключения Realtime;
- при возврате на сохранённый экран через Back;
- при возврате приложения из фона.

В этом варианте первоначальным запросом управляет listener: отдельно такой же
запрос в On Page Load не нужен. Подключение подписки также вызывает контрольное
чтение, чтобы закрыть промежуток между первым чтением и установкой подписки.
Быстрые сигналы объединяются за 500 мс; одновременно выполняется только один
callback. Если изменения пришли во время RPC, после ответа будет ещё одно чтение.
Скрытые страницы и приложение в фоне не выполняют RPC.

При выборе фильтра обновить `selectedPeriod` с rebuild страницы. Это изменит
`refreshKey` и инициирует чтение. Не вызывать одновременно второй такой же RPC
отдельным действием фильтра. Для Pull to Refresh обновить `refreshDate`.
App State нужно обновлять с rebuild страниц, чтобы listener увидел новое значение.

## 5. После завершения игры

После успешной записи `status = completed` и рассчитанного `lichtwatt`, а затем
перехода на профиль/рейтинг, listener загрузит свежие показатели.
Если запись делает асинхронный серверный обработчик, новый результат появится
после его фактической записи: Broadcast вызовет дополнительное чтение.
Вызов текущего `refresh` при входе на FinishPage сам по себе не доказывает,
что начисление уже закончено. По желанию после подтверждённого начисления
обновить `AppState.refreshDate` существующим механизмом refresh.

Для GoodGamesPage использовать тот же listener с callback загрузки рейтинга
и refreshKey из периода/категории. Ему нужна отдельная расчётная RPC для
страницы списка с пагинацией и отдельным текущим пользователем: её этот
пример не создаёт.

Убирать полные запросы games/invites для расчётов нужно только после привязки
всех зависимых значений к RPC. Запросы истории игр/приглашений для самих списков
остаются, с фильтрацией и пагинацией.

## Проверка подключения после разрешённого применения

1. Прямой вызов RPC возвращает нужный профиль и выбранный период.
2. Два клиента: завершение игры в A обновляет очки/места в открытом профиле B.
3. Изменение/удаление завершённой игры или использованного приглашения
   обновляет показатели и для старого сезона.
4. Быстро переключить период во время медленного запроса: старый ответ
   не заменяет данные нового фильтра.
5. Back, возврат из фона и переподключение сети выполняют свежее чтение.
6. Проверить гостевой просмотр и что raw invites по-прежнему защищены RLS.

RPC считает по исходным таблицам на каждом запросе. Это убирает загрузку всех
строк на устройство, но не устраняет стоимость SQL-агрегации. Индексы и план
запроса нужно проверить на реальных данных; для высокой частоты изменений
возможен следующий этап с синхронно обновляемыми агрегатами и тем же клиентским
контрактом. Broadcast не заменяет постоянное хранение результатов и может
пропускать события при разрыве связи, поэтому предусмотрены повторные чтения.
